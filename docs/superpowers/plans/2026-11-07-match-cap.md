# Match Cap Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Impedir que uma região grave mais partidas que o teto configurado para cada patch.

**Architecture:** O serviço consulta um cache de contagens Mongo por `(patch, region)`, válido por 60 segundos, antes do `poll` e após descobrir o patch no detalhe. O adapter expõe a contagem e o status deriva as mesmas contagens para os patches aceitos.

**Tech Stack:** Spring Boot 4, Java 25, MongoTemplate, JUnit 5, Mockito.

**Spec:** issue allanmaslopes/yoursummoner_collector#5 (pedido do usuário em 2026-11-07)

## Global Constraints

- `collector.max-matches-per-patch` padrão `15000`; `0` desabilita o teto.
- Não armazenar identificadores de jogador na coleção `matches`.
- Contagem Mongo deve filtrar `patch` e `region`; índice composto correspondente.
- Cache por `(patch, region)` deve reler no máximo a cada 60 segundos.
- Não usar Git; Spring/Mongo não executam no sandbox.

## Review Focus

- Teto igual à contagem: deve bloquear, não apenas valores maiores (PipelineTest).
- Uma região com todos os patches aceitos no teto não pode fazer `poll` (PipelineTest).
- Patch conhecido no detalhe, mas no teto, não pode pedir timeline (PipelineTest).
- Valor zero não pode bloquear nenhum patch (PipelineTest).
- Status deve reportar todas as versões aceitas e `capped` coerente (StatusControllerTest).
